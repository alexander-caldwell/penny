Know what every dbt model actually costs.

Penny reads BigQuery's own record of every query it ran, traces each one back to the dbt model that caused it, and turns bytes into dollars. Per model, per day, with trends and anomaly flags.

After every run

Penny prints what the run cost to your console, split into the models themselves and the hooks around them.

Why bother

Cost you can act on

A warehouse bill tells you what you spent. It does not tell you which model to look at on Monday morning.

Per model, not per run

Every job is traced to the model that caused it, including the hooks that ran around it and the temporary tables an incremental build creates.

Trends and anomalies

Daily cost against a rolling 30-day average, a weekly trend per model, and a red, amber or green flag when a model costs more than it should.

Useful with no setup

Penny works with zero labels and gets sharper as you give it more identity. Two lines of configuration is the whole installation.

Mixed billing handled

On-demand and reserved jobs are priced separately, job by job, so a project that mixes both is still costed correctly.

History that outlives BigQuery's

BigQuery keeps job history for 180 days. Penny's tables do not expire, so running it daily is how you keep cost history for longer.

Nothing to run

No agent, no scheduler, no external service. It is a dbt package that reads metadata already sitting in your warehouse.

Install

Three steps

Configuration only. No change to the SQL you run or the data it produces.

Add the package

In packages.yml:

{% raw %}
packages:
  - git: "https://github.com/alexander-caldwell/penny.git"
    revision: v0.1.10
{% endraw %}

Label your jobs

In dbt_project.yml. The query comment stamps each BigQuery job with the model that ran it; the hook prints the summary.

{% raw %}
query-comment:
  comment: "{{ penny.penny_query_comment(node) }}"
  job-label: true

on-run-end:
  - "{{ penny.log_run_costs() }}"
{% endraw %}

Build

Penny writes its own models into a penny schema.

dbt deps
dbt build --select penny

Install v0.1.9 or later. Earlier tags from v0.1.6 read a column that INFORMATION_SCHEMA.JOBS does not have in every region.

What you get

Five tables, raw jobs up to a per-model view

TableOne row perTells you
stg_bigquery__job_history BigQuery job The raw facts, straight from job metadata
int_penny_model_runs BigQuery job Cost per job, tagged build, hook or overhead
rpt_penny_cost_summary Model per day Daily cost, 30-day rolling average, anomaly flag
rpt_penny_cost_by_layer Layer per day Where spend concentrates across your layers
rpt_penny_model_latest Model Latest state, weekly trend, red/amber/green status
Pricing

How a job becomes a number

Two formulas, chosen per job by whether it ran inside a reservation.

On-demand

The job ran outside a reservation, so you paid for bytes.

bytes_billed ÷ 1 TiB × price per TiB

Slot-based

The job ran inside one, so you paid for time.

slot_ms ÷ 1 hour × price per slot-hour

Prices come from your configuration, not from the warehouse, so set them to your contracted rate. Penny reports gross cost: BigQuery's free tier is account-level and cannot be split across models.
